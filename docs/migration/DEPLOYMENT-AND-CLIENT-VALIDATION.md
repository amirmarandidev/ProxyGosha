# TypeScript deployment and independent-client validation

## Current configuration

`wrangler.jsonc` now points to `src/index.ts`. The original `worker.js` remains in
the repository, unchanged, and can be selected again by restoring `main` to
`worker.js`. A separate `wrangler.baseline.jsonc` config deploys that JavaScript
implementation under the distinct Worker name `proxy-gosha-js-baseline` for
side-by-side client comparison.

The configured compatibility date is `2026-11-13`. The operator reported that the
compatibility-date check passed against the original deployment's date. If that
was not the date shown in the original Worker's Runtime settings, stop and correct
both Wrangler configs before deployment.

## 1. Build and local checks

Run all checks from the repository root:

```powershell
npm run check
npm run smoke:worker
npm run test:e2e
npm run test:tcp-integration
npm run test:protocol-diff
npm run test:workerd-tcp:all
npm run check:compatibility-date
```

The `test:workerd-tcp` command requires Wrangler installed by `npm install`.
The compatibility check requires the verified original date to be supplied in
`PROXY_GOSHA_BASELINE_COMPATIBILITY_DATE`.

## 2. Deploy a JavaScript baseline for comparison (optional but recommended)

This creates a separate Worker; it does not replace the existing production Worker:

```powershell
npx wrangler deploy --config wrangler.baseline.jsonc
```

Set the required secrets/bindings on that baseline Worker using the same intended
configuration as the TypeScript candidate. Do not copy secrets into config files or
commit them. Keep the two Workers on separate hostnames.

## 3. Deploy TypeScript to a staging Worker

Deploy the current TypeScript entry point under a separate name:

```powershell
npx wrangler deploy --config wrangler.jsonc --name proxy-gosha-ts-staging
```

The TypeScript config includes a SQLite-backed Durable Object class export for the
`CONTROL_PLANE` binding. Wrangler provisions its namespace during deployment.
Set the staging Worker's `ADMIN_KEY`, `SECRET`, and any other required variables
through the Cloudflare dashboard or `wrangler secret put`. The Durable Object uses
`ADMIN_KEY` to authenticate runtime settings updates. Use the same effective proxy
configuration as the baseline. The settings API and global telemetry are available
only on the TypeScript candidate; the JavaScript baseline has no `CONTROL_PLANE`. Do not set `E2E_TEST_MODE`, `E2E_DC_HOST`, or
`E2E_DC_PORT` on either deployed Worker. Do not attach the production custom domain
to staging.

Open the staging Worker URL, visit its admin panel, and use its generated Telegram
WEB proxy link to add the proxy to Telegram Desktop. The app must support Telegram's
WEB proxy type. Disable other proxies temporarily so the test result is attributable
to this Worker.

## 4. Independent Telegram-client acceptance test

Use the same Telegram Desktop installation/account and network for both Workers.
Test the JavaScript baseline first, then the TypeScript staging Worker. For each:

1. Add the WEB proxy using the link generated by that Worker's own admin panel.
2. Select that proxy as the active proxy in Telegram Desktop.
3. Confirm Telegram reports the proxy as connected and the client can load the chat list.
4. Open an existing chat, send and receive a text message, and verify message updates arrive.
5. Open a media item and confirm it loads; optionally send a small file.
6. Disconnect/reconnect the proxy and confirm the client recovers.
7. Repeat the same sequence against the other Worker.

Record the Telegram Desktop version, OS, network, Worker URL, carrier mode, and any
errors. Do not share proxy secrets, admin keys, session tokens, or private messages
in test logs. A passing local test requires both baseline and TypeScript candidates
to complete the same sequence. If the baseline works and TypeScript fails, do not
move the production domain.

This manual test is the independent-client interoperability check. It cannot be
executed from this repository's automated test environment because it requires a
real Telegram Desktop client, an authenticated Telegram account, and deployed Worker
URLs. No result is claimed until the operator completes it.

## 5. Production deployment

Only after the TypeScript staging Worker passes the client test:

1. Confirm production secrets and non-secret bindings are present and unchanged.
2. Confirm the production Worker name, routes, custom domains, and compatibility date.
3. Deploy the TypeScript config to the existing production Worker:

   ```powershell
   npm run deploy
   ```

4. Run the HTTP smoke checks against the production URL: setup/admin page, health,
   session bootstrap, WebSocket authentication, and Telegram Desktop connectivity.
5. Keep the previous `worker.js` version available in Cloudflare deployment history.

After deploying the Durable Object `exports` lifecycle, roll back the production
Worker by changing `main` in `wrangler.jsonc` to `src/baseline-entry.js` and
redeploying while keeping the `CONTROL_PLANE` binding and `exports` declaration.
That wrapper serves the untouched original `worker.js` while continuing to export
the Durable Object class required by Wrangler. Do not remove the `exports` lifecycle
as part of an ordinary rollback.

## Deployment boundary

This repository change configures TypeScript as the deployment entry point and
provides a staging/baseline procedure. It does not itself authenticate to Cloudflare,
create deployed Workers, set secrets, assign routes, or move a production custom
domain. Those operations must be run by an operator with access to the Cloudflare
account.
